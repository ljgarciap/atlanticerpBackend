## Hallazgos

### MEDIO — CORREGIDO en 1ee54a7 (ver Pasada 2) — FE mandaba `fe_reintento_max_horas: null` al vaciar el campo y el backend lo rechaza con 422
- Criterio incumplido: (3) parámetro configurable 1–720 en Configuración Fiscal; contrato FE↔BE (shape mismatch nº6).
- El schema Zod del FE trata el campo como "opcional: vacío = null (el backend aplica su default)" y el payload del PUT sí lleva `fe_reintento_max_horas: null` (probado con vitest: `PAYLOAD fe_reintento_max_horas = null has key: true`). El backend (`UpdateFiscalSettingsRequest`: `sometimes|integer|min:1|max:720`, sin `nullable`; la columna es NOT NULL default 24) responde **422** a `null` (probado por HTTP real: `null => 422`, `"" => 422`, `[] => 422`).
- Efecto: Aprobador vacía el campo y guarda -> no se guarda NADA de la pantalla (los demás campos tampoco) y ve un texto de error de Laravel ("El campo fe reintento max horas debe ser un número entero.") en vez del mensaje del FE. No hay pérdida de datos ni se rompe la FE; es un bloqueo de UX contradictorio con la ayuda del campo. El test del FE se llama "vacío va como null" pero no lo ejercita (solo prueba 999 y 48).
- Fix propuesto (1 línea, FE): en `buildSchema` hacer el campo obligatorio, sin preprocess/nullable: `z.coerce.number().int(msg).min(1,msg).max(720,msg)` (vacío -> 0 -> falla `min(1)` con el mensaje propio). Alternativa BE: aceptar `nullable` y omitirlo en el servicio. Evidencia permanente añadida: `atlanticerp-frontend/.worktrees/fe-1019/src/components/FiscalSettingsPanel.preqa1019.test.tsx` (usa `it.fails`: hoy pasa porque el comportamiento está roto; cuando se corrija vitest lo marcará para quitar `.fails`).
- Nota: `makeSettings()` de los tests existentes no incluye `fe_reintento_max_horas`, por eso nunca se vio.

### MENOR (informativo, no bloquea)
1. Reglas de "ya certificado": el éxito 200 exige que el texto contenga "ya certificado previamente" (en `mensaje|message|detalle|error`, insensible a mayúsculas) **y** CUFE no vacío. Un 200 con CUFE pero otro texto cae a `error_configuracion` (verificado). Es lo seguro (falla cerrado) pero depende del literal de MSL (respuesta de Edgar 2026-10-02); si MSL cambia la frase, la idempotencia deja de reconocerse sin avisar. Recomendable dejar el literal como constante documentada (ya está en un solo método).
2. Borde exacto de la ventana: a las 24 h 00 min 00 s exactas aún REENVÍA (`lt(now()-24h)` es estricto); 23:59 reenvía; 24:01 bloquea. Es coherente con "más de 24 horas" y con el mensaje "pasaron más de 24 horas".
3. `fe_reintento_max_horas` = 0 solo es alcanzable por BD (la API valida 1–720, columna NOT NULL default 24); el código lo trata como "sin límite". Inalcanzable hoy; dejarlo anotado.
4. `POST correccion/preview` con un `factura_origen_id` que no existe en absoluto devuelve 422 de validación (`exists`), no el 404 en español; el 404 en español aplica a una factura existente ya anulada (probado en preview y en registro). Comportamiento previo, no regresión.
5. Reconciliar y "Actualizar estado" conviven para `pendiente` (dos botones con confirmaciones independientes) — redundante pero inocuo; reconciliar sobre un `pendiente` fuera de ventana cuyo GET da 404 lo pasa a `error_configuracion` (documentado en el mensaje).
6. `mslYaTieneLaFactura` hace un GET a MSL dentro del `lockForUpdate` de la corrección: latencia/timeout de MSL retiene la fila; falla cerrado (422 "no se pudo verificar") — aceptable, solo observar.
