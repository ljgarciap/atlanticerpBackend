## SCRUM-746 — 1 CRÍTICO real encontrado y corregido (loop cerrado, no diferido)

**CRÍTICO — `session_inactivity_hours` no tenía ningún campo en la UI de Configuración.**
Verificado en código antes de tocar el navegador (Paso 0 del protocolo — valor paramétrico de
negocio): el backend ya tenía el valor en `auth.system_settings`, validado (`min:1, max:720` en
`SettingsController`/`PreferencesService`) y gateado por `permission:settings.global` — pero
`atlanticerp-frontend/src/pages/SettingsPage.tsx` y `src/api/settingsApi.ts` (interfaz `SystemSettings`)
nunca se actualizaron para exponerlo. Efecto real: la única forma de cambiar el timeout de
inactividad era una llamada directa a la API (curl/Postman) — ningún superadmin podía ajustarlo
"sin deploy" desde la UI, incumpliendo la regla dura del CLAUDE.md raíz ("todo umbral/margen de
negocio va en tabla paramétrica configurable, **con CRUD y vista de administración**"). El criterio
de aceptación 1 del ticket ("tiempo configurable, default 10h") tampoco se cumplía de forma
utilizable para un administrador real.

**Fix aplicado en el momento** (mismo patrón exacto que `ShareLinksExpirationInput`, ya usado en la
misma pantalla para `share_links_expiration_days`):
- `atlanticerp-frontend/src/api/settingsApi.ts` — agregado `session_inactivity_hours: number` a la
  interfaz `SystemSettings`.
- `atlanticerp-frontend/src/pages/SettingsPage.tsx` — nuevo `SettingRow` + componente
  `SessionInactivityHoursInput` (rango 1-720, mismo mecanismo de validación cliente que el de
  links compartidos, dentro de la sección "Configuración global" ya gateada por
  `settings.global`/`superadmin.all`).
- `src/i18n/locales/{es,en}/settings.json` — 4 keys nuevas (`sessionInactivityHours*`).

**Re-verificación completa tras el fix** (checklist completo del ticket, no solo el punto que
faltaba):
- `tsc --noEmit` limpio, `npm run build` exitoso, suite completa de frontend **1152/1152 tests
  verdes** (110 archivos) — sin regresiones.
- UI real (Playwright): superadmin (`luis.garcia`) ve el campo "Expiración de sesión por
  inactividad" con valor 10 (default) y lo puede guardar; usuario `vendedor_disenador`
  (`neil.quiel`, sin `settings.global`) **no ve la sección "Configuración global" en absoluto**
  (confirmado visualmente, screenshot `e2e/.tmp/scrum746/settings-luis-scrolled.png` /
  `settings-neil.png`).
- API directa: `PATCH /api/settings/system {session_inactivity_hours: 5}` → 200, persiste;
  `{session_inactivity_hours: 0}` → 422 ("debe ser al menos 1"); `{721}` → 422 ("no debe ser mayor
  que 720"); mismo request con el token de `neil.quiel` (sin `settings.global`) → 403. Valor
  restaurado a 10 (default) al terminar.

**Gate combinado de inactividad/techo absoluto (núcleo del ticket) — 4 escenarios verificados
contra el mecanismo REAL (`POST /auth/refresh`), manipulando `last_activity_at`/`login_at` en
`refresh_tokens` vía SQL directo y llamando al endpoint real:**

| Escenario | Manipulación | Resultado | Esperado |
|---|---|---|---|
| Camino feliz | `last_activity_at`/`login_at` recientes | `200`, rotación exitosa, `login_at` se propaga sin resetear | ✅ |
| Inactividad > 10h | `last_activity_at` = hace 11h | `401` | ✅ |
| Techo absoluto 30 días, actividad constante | `login_at` = hace 31 días, `last_activity_at` reciente | `401` (rechaza igual, el techo NO se resetea por actividad) | ✅ |
| Dentro del techo | `login_at` = hace 29 días, `last_activity_at` reciente | `200`, acepta | ✅ (confirma el borde de los 30 días, no solo el caso obvio) |

Confirmado además:
- El `UPDATE ... WHERE ... RETURNING` es atómico — un intento de refresh sobre un token ya vencido
  por inactividad **no revive** `last_activity_at` (verificado: el valor manipulado a "hace 11h"
  quedó intacto tras el intento fallido, no se sobrescribió a `now()`).
- `login_at` sobrevive la rotación (confirmado en DB: token hijo hereda el `login_at` del padre,
  nunca se resetea a `now()` en cada refresh) — el techo de 30 días es real, no rodante.
- `auth.token_refreshed` se loggea en `audit_logs` en cada rotación exitosa (2 entradas
  confirmadas para las 2 rotaciones exitosas del escenario, 0 para los 2 rechazos — correcto, solo
  se audita lo que realmente rota).
- Mecanismo de refresh silencioso (`src/lib/silentTokenRefresh.ts`): confirmado que el interceptor
  de `authApi.ts` invoca `handleSilentRefresh` en cada respuesta 2xx exitosa (`api.interceptors.
  response.use`). No se esperó en tiempo real ~57 min (buffer de 3 min antes del `exp` de
  `session_timeout_min`, default 60 min) para observarlo disparar solo en el navegador — cubierto
  en cambio por la suite de 9 tests unitarios de `silentTokenRefresh.test.ts` (dedupe, buffer,
  exclusión de rutas públicas, manejo de fallo), **9/9 verdes**, que ejercitan exactamente esa
  lógica de decisión con tiempos simulados.

**Limpieza post-pruebas (confirmado explícito, ver instrucción del despacho):** todas las filas de
`refresh_tokens` manipuladas manualmente vía SQL (`id` 1866-1869, usuario `neil.quiel`) se
revirtieron a valores consistentes con su `created_at` real (no un valor arbitrario) — sin
`last_activity_at`/`login_at` tampeados apuntando al pasado quedando asociados a la cuenta real.
Adicionalmente, la corrida final de `infra/test.sh` (ver sección "Regresión" abajo) truncó
`refresh_tokens` por completo como efecto secundario normal de la suite compartiendo Postgres con
el dev local (gotcha ya documentado en el CLAUDE.md del proyecto) — la tabla quedó en 0 filas,
ninguna sesión de las cuentas reales usadas queda con datos manipulados.

## SCRUM-748 — Pre-QA (comando backend, sin UI — Visual Review N/A)

Corrido con `--count=5` (no 40, para no inflar el stack local) contra el tenant `illuminations`:

| Corrida | Resultado |
|---|---|
| 1ª, `--count=5` desde 0 | Crea 5, todos `approved`, 5/5 con `Order` en Bodega. Distribución: 5 vendedores distintos (round-robin). |
| 2ª, `--count=5` (idempotencia) | "Ya hay 5... nada que crear." — no duplica. |
| 3ª, `--count=8` (top-up) | Crea exactamente 3 más (5→8), no re-crea los 5 existentes. |
| `--count=0` | Rechaza: "--count debe ser >= 1." (exit 1, no crashea). |
| `--count=-3` | Rechaza igual, mismo mensaje. |

**Verificación por SQL directo** (no solo el output del comando): los 8 `Order` de Bodega existen
en `illuminations_bodega.orders` con `pipeline_card_id` correcto, vinculados a sus
`PipelineCard`/`SalesProject` `[UAT-BODEGA]` en etapa `approved` — confirmado con JOIN explícito a
las 3 tablas, no solo el resumen que imprime el propio comando.

**Limpieza post-prueba (confirmado explícito):** las 8 filas de `Order`,
`PipelineCard`/`PipelineCardContact`/`PipelineCardDeliveryDate`/`PipelineCardFile`,
`SalesProject`, `SubClient` y `MasterClient` marcadas `[UAT-BODEGA]` se borraron por completo
(DELETE directo por SQL, respetando el orden de FKs) — verificado con un `SELECT count(*)` final
en 0 para las 5 tablas. Se corrió una verificación adicional de "correr desde 0 otra vez" (`--count=1`)
para confirmar que el comando sigue funcionando limpio tras la limpieza, y esa corrida también se
limpió.
