## Hallazgos — Senior Review (revisión estática de código)

### CRÍTICO — SCRUM-884: dos rutas de producción dejaban `created_by` en NULL para siempre, no solo en datos históricos

**Causa raíz:** `PipelineService::create()` sí poblaba `created_by` correctamente, pero es solo
UNA de tres vías reales que crean un `PipelineCard`:
- `ClientsService::createLeadCard()` — el Lead automático (REQ-068), disparado cada vez que se
  crea un Cliente/Subcliente nuevo. Vía de uso muy frecuente.
- `QuoteService::resolveLinkedCardForConfirm()` — cuando se confirma una cotización sobre un
  proyecto que todavía no tiene tarjeta de Pipeline (cotización creada directo, sin pasar por
  Lead/Diseño primero).

Ninguna de las dos pasaba por `PipelineService::create()`, así que cualquier proyecto nacido por
esas dos vías quedaría con `created_by = NULL` **para siempre**, incumpliendo directamente el
criterio de aceptación "todo proyecto muestra un campo Creador" — no es un problema que el
backfill de datos históricos resuelva, porque afecta a proyectos nuevos también.

**Fix:** ambos métodos ya recibían el id de quien origina el proyecto (`$ownerId`/
`$quote->owner_id`, usado para poblar `owner_id`) — se agregó el mismo valor a `created_by`.
**Verificación:** tests de integración agregados en `ClientsControllerTest` y `QuoteControllerTest`
que ejercitan exactamente estos dos caminos y aseveran `created_by`.

### MEDIO — SCRUM-907: listado global de Arquitectos sin ningún tope

`ArchitectController::index()` en modo global (sin `sub_client_id`) no tenía límite — mismo tipo de
descuido que causó SCRUM-917 (aunque acá sin el bug de orden limit-antes-de-filtro: el `where`/
`ilike` sí corre en SQL antes de cualquier límite). Hoy son 15 arquitectos reales en dev, sin
impacto — se agregó `GLOBAL_LIST_LIMIT=500` por higiene, para no repetir el patrón que ya costó un
ticket completo.

## Hallazgo — Pre-QA (adversarial, app real)

### MEDIO — SCRUM-907: mensaje de error genérico al fallar el guardado de Arquitecto

**Escenario de ruptura:** en el detalle de un Arquitecto, entrar a Editar, borrar Teléfono Y Correo
(el backend exige al menos uno) y guardar.

**Resultado antes del fix:** `ArchitectDetailModal` solo leía `err.response.data.message` —
Laravel devuelve ahí el genérico `"The given data was invalid."`, nunca el motivo real
(`errors.phone[0]`: "El teléfono es obligatorio si no hay correo"). El usuario veía un mensaje
inútil sin saber qué corregir.

**Fix:** mismo patrón ya usado en `ClientDetailModal::contactErrorMessage()` — priorizar el primer
mensaje de `errors` sobre el `message` genérico.
