## SCRUM-132 (REQ-040) — Margen mínimo del 30% — ❌ CRÍTICO, no implementado

**CRÍTICO — la validación de margen mínimo no existe en ningún punto del sistema.** Confirmado
tanto por lectura de código como por ejecución real:

- `QuoteItemController::update()` no tiene ninguna validación de margen — acepta cualquier
  `unit_price`/`discount_percent` sin comparar contra `cost`.
- `QuoteController::validateTotalsDiscount()` lo documenta explícitamente en su propio docblock:
  *"La validación de margen mínimo (REQ-040) no aplica todavía porque no hay costo de catálogo de
  referencia"* — pero esa premisa ya no es cierta: el Catálogo real con costo (`catalog_products.
  cost`) existe desde SCRUM-116-124 (productos SPOT-001/LAMP-002, cost 22/60).

Ejecutado en navegador real sobre `PREQA-CUSTOM-1` (unit_price=100, cost=50, margen sano 50%):

| Editar unit_price a 10 (margen -400%, vender bajo costo) | Revierte + avisa | Se guarda "10" tal cual, SIN aviso ni reversión |
| Descuento de línea 90% (precio efectivo 10, muy bajo el costo 50) | Revierte + avisa | Se guarda "90%" tal cual, SIN aviso ni reversión |

No se pudo ejercer el resto de las vías que pide el criterio 2 (descuento global, cambio de tipo de

El criterio 3 ("producto personalizado sin costo -> no aplica") es trivialmente cierto hoy (nunca

## SCRUM-133 (REQ-041) — Descuento por línea o global — ❌ CRÍTICO, UI desincronizada tras reset

| Escenario de ruptura intentado | Resultado |
|---|---|
| Modo "Por línea": columna Descuento % visible, campo global oculto | ✅ correcto |
| Cambiar a "Global": columna por línea desaparece, campo global se habilita | ✅ correcto (visualmente) |
| Confirmado en BD: al cambiar a Global, `discount_percent` de TODOS los ítems se resetea a 0 server-side | ✅ correcto (`resetDiscountsForModeSwitch`) |
| **Volver de "Global" a "Por línea"** y mirar de nuevo el campo de descuento del mismo ítem | ❌ **la fila muestra el valor VIEJO (10%) en pantalla, aunque el valor real en BD es 0** (confirmado por SQL en paralelo) |

**CRÍTICO — causa raíz:** `QuoteItemRow` (`atlanticerp-frontend/src/components/QuotePartCard.tsx`)
inicializa su estado local `draft` una sola vez con `useState(draftFromItem(item))` y nunca lo
resincroniza cuando el `item` recibido por props cambia tras un refetch — porque React reutiliza la
misma instancia del componente (`key={item.id}`, el id no cambia) en vez de remontarla. El
reset del backend al cambiar de modo SÍ ocurre (confirmado en BD), pero la fila nunca se entera:
sigue mostrando el descuento antiguo hasta que el usuario recarga la página a mano.

**Riesgo real, no solo cosmético:** como `isDirty` compara `draft` (viejo) contra
`original = draftFromItem(item)` (recalculado en cada render desde el `item` fresco), la
discrepancia hace que el botón "Guardar" de esa fila aparezca aunque el usuario no haya tocado
nada — y un click ahí **reenvía el 10% viejo al backend, deshaciendo silenciosamente el reset que
el propio criterio de aceptación exige**.

**Vuelve a Dev Testing.** Recomendación: sincronizar `draft` con `item` vía `useEffect(() => {
setDraft(draftFromItem(item)) }, [item])`, o forzar remount con una `key` que incluya un valor que
cambie en el reset (ej. `key={`${item.id}-${item.discount_percent}-${item.price_type_override}`}`)
— la primera opción es más robusta porque cubre cualquier campo que cambie por una vía indirecta
(no solo el reset de modo), no solo los dos que se testearon acá.

## Nota metodológica — creación duplicada de cotización en `npm run dev`

Cada `POST /quotes` (crear borrador) se disparó DOS VECES seguidas durante las pruebas —
confirmado en BD (pares de quotes con el mismo `created_at` exacto, ids consecutivos). Causa: el
`useEffect` de auto-creación en `QuotePage.tsx` corre bajo `React.StrictMode`, que en modo
desarrollo invoca efectos dos veces a propósito. **Esto NO ocurre en el build de producción**
(dev.atlanticerp.ai/test.atlanticerp.ai/atlanticerp.ai sirven el bundle compilado, sin StrictMode) — no es un bug
reportable, solo una particularidad del entorno de desarrollo local a tener en cuenta si se
vuelve a automatizar Playwright contra `npm run dev`.
